# אפיון מערכת: דרישות תשלום מדרסה

מסמך זה מתאר את אפליקציית דרישות התשלום של מדרסה כפי שהיא צריכה לפעול בגרסת מפגשים. המערכת בנויה כ-Next.js App Router עם TypeScript ו-Tailwind, ללא בסיס נתונים, ועובדת ישירות מול Monday.com דרך GraphQL API.

## 1. עקרון מוצר מרכזי

הטופס למורה אינו מציג סכומים, תעריפים, צפי תשלום, יתרת כסף או סכום להעברה. כל חוויית המשתמש מבוססת על יחידות הוראה בלבד:

- במסלול קורס והחלפה: מפגשים.
- במסלול שיעורים פרטיים: שיעורים.
- במסלול אחר: פירוט חופשי ובדיקה ידנית.

הסכומים עדיין נדרשים לבורד דרישות התשלום במאנדיי, אבל הם מחושבים פנימית בצד השרת לפי נתוני הקורס או מסומנים לבדיקה ידנית אם חסר מידע אמין.

## 2. סטאק וארכיטקטורה

- Framework: `Next.js 15` עם App Router.
- Language: `TypeScript`.
- UI: `Tailwind CSS` ורכיבי UI בסגנון `shadcn/ui`.
- Direction: RTL מלא בעברית.
- Storage: אין DB. בחירות המורה נשמרות זמנית ב-`sessionStorage`.
- External API: Monday GraphQL API בלבד.
- Deployment: Vercel או סביבת Node תואמת.

שכבות מרכזיות:

- `app/`: מסכי wizard ו-API routes.
- `lib/monday/`: קבועי Monday, טיפוסים, client, queries ו-preview mocks.
- `lib/payment/`: מנוע עסקי של מסלולים, ולידציית מפגשים וחישוב סכומים פנימי.
- `lib/session.ts`: שמירת session וסיכום הגשה ללא DB.

## 3. משתני סביבה

```env
MONDAY_API_TOKEN=<לא לשמור בקוד>
MONDAY_API_URL=https://api.monday.com/v2
MONDAY_PREVIEW_MODE=true # אופציונלי לפיתוח ללא Monday אמיתי
```

אם `MONDAY_PREVIEW_MODE=true`, ה-API routes מחזירים נתוני mock ולא יוצרים פריטים אמיתיים במאנדיי.

## 6. שדות חדשים נדרשים במאנדיי

השדות הבאים חייבים להיווצר בבורד דרישות תשלום. עד שלא יהיו Column IDs אמיתיים, הקוד שומר אותם ב-`PAYMENT_REQUEST_MEETINGS_COLUMNS` כ-`null` ומחזיר configuration error ברור בזמן יצירת פריט אמיתי.

| שם מוצע | סוג | שימוש |
|---|---|---|
| מספר מפגשים בדרישה | numbers | כמה מפגשים/שיעורים מוגשים בדרישה הנוכחית |
| מספר מפגשים בקורס בעת ההגשה | numbers | snapshot של מספר המפגשים הכולל בקורס |
| סוג דרישת קורס | status | `קורס מלא`, `קורס חלקי`, `החלפה`, `השלמה / תיקון`, `שיעורים פרטיים`, `אחר` |
| דורש בדיקה ידנית | status או checkbox | מומלץ status: `תקין`, `דורש בדיקה`, `דרישה ישנה ללא נתוני מפגשים`, `חריגה ממספר מפגשים` |

## 7. קונפיגורציית מסלולים

המערכת אינה טופס גנרי חסר לוגיקה; היא מנוע דרישות עם קונפיגורציה למסלולים. הקובץ `lib/payment/config.ts` מגדיר:

```ts
type PaymentRouteConfig = {
  routeKey: "course" | "replacement" | "private" | "other";
  label: string;
  sourceBoardId?: number;
  allowedCourseStatuses?: string[];
  unitLabel: "מפגשים" | "שיעורים" | "יחידות";
  requiresCourse: boolean;
  requiresReplacedTeacher?: boolean;
  requiresManualDescription?: boolean;
  calculationMode: "course_meetings" | "private_lessons" | "manual";
};
```

מסלולים קיימים:

- `course`: קורסים שהסתיימו בלבד, יחידת מפגשים, חישוב לפי קורס.
- `replacement`: קורסים בסטטוס `קורס רץ` או `הסתיים`, יחידת מפגשים, דורש מורה שהוחלף.
- `private`: שיעורים פרטיים פעילים, יחידת שיעורים.
- `other`: פירוט חופשי, בדיקה ידנית.

## 8. UX נדרש

### מסך 1: זיהוי מורה

- בחירת מורה פעיל מתוך רשימת Monday.
- בדיקת תיק ספק אחרי בחירה.
- אם תיק ספק חסום, מוצג מסך חסימה ולא ניתן להמשיך.
- אם תיק ספק תקין, מוצגת בחירת סוג דרישה.

### מסך 2: בחירת סוג דרישה

אפשרויות:

- קורס
- החלפה
- שיעורים פרטיים
- אחר

### מסך קורס

מוצגים רק קורסים של המורה בסטטוס `הסתיים`.

בבחירת קורס מוצג:

- שם הקורס.
- תאריך התחלה וסיום.
- מספר מפגשים בקורס.
- כמה מפגשים כבר הוגשו בדרישות פעילות.
- כמה מפגשים נותרו זמינים להגשה.
- רשימת דרישות קיימות ללא סכומים.

המורה מזין רק מספר מפגשים להגשה.

### מסך החלפה

מוצגים קורסים של המורה שהוחלף בסטטוס `קורס רץ` או `הסתיים`.

שדות:

- את מי החלפתי.
- קורס.
- מתי החלפתי.
- כמה מפגשים החלפתי.
- פירוט קצר אופציונלי.

### מסך שיעורים פרטיים

מוצגות הרשמות פעילות בלבד:

- `שובץ מורה`
- `נשלח מייל למורה`
- `תואם ורץ`

מוצג:

- שם תלמיד.
- שיעורים שנרכשו.
- שיעורים שהתקיימו.
- שיעורים נותרים.

המורה מזין רק מספר שיעורים לתשלום.

### מסך אחר

שדה פירוט חופשי בלבד. הדרישה נשלחת לבדיקה ידנית.

### מסך הצלחה

מסך הצלחה מציג:

- סוג הדרישה.
- נושא הדרישה.
- מספר מפגשים/שיעורים אם קיים.
- האם נשלחה רגיל או לבדיקה ידנית.

אין במסך הצלחה סכומים או תעריפים.

## 9. לוגיקה עסקית

### קורס

1. שולפים רק קורסים שהסתיימו.
2. לאחר בחירת קורס שולפים את מצב המפגשים.
3. סופרים רק דרישות פעילות על אותו קורס.
4. דרישות בסטטוס `נדחה/ בוטל/ שגוי` לא נספרות.
5. אם קיימת דרישה ישנה ללא מספר מפגשים, לא מנחשים ומסמנים בדיקה ידנית.
6. אם לאחר ההגשה סך המפגשים עובר את מספר המפגשים בקורס, הדרישה נשלחת עם סטטוס `ממתין לבירור / תיקון`.

### החלפה

החלפה יכולה לקרות גם בקורס רץ, ולכן מסלול זה כולל `קורס רץ` ו-`הסתיים`.

אם סך המפגשים לאחר דרישת ההחלפה עובר את מספר המפגשים בקורס, הדרישה לא נחסמת, אך מסומנת לבדיקה ידנית כדי שהצוות יוכל לבדוק קיזוז מול הדרישה המקורית.

### שיעורים פרטיים

המסלול נשאר מבוסס שיעורים בלבד. אם אין שדה תעריף אמין לחישוב פנימי, הדרישה נוצרת לבדיקה ידנית במקום לנחש.

### אחר

מסלול חופשי. הדרישה תמיד נשלחת לבדיקה ידנית.

## 10. פונקציות שירות

נדרשות וממומשות שכבות שירות שאינן בתוך React components:

- `getEligibleCoursesForPayment(teacherId)`: קורסים שהסתיימו בלבד.
- `getEligibleCoursesForReplacement(teacherId)`: קורסים רצים או שהסתיימו.
- `getCourseMeetingsState(courseId)`: מצב מפגשים ודרישות קיימות.
- `validateMeetingsSubmission(input)`: ולידציית מפגשים.
- `calculateInternalAmountsForCourseClaim(input)`: חישוב סכומים פנימי.
- `submitPaymentRequest(payload)`: יצירת פריט במאנדיי עם סטטוס מתאים.

## 11. חישוב סכומים פנימי

החישוב אינו נחשף למורה.

Inputs:

- `courseTeachingRate` מתוך `numeric`.
- `courseTravelRate` מתוך `numeric1`.
- `totalMeetings` מתוך `numbers9`.
- `requestedMeetings` מהטופס.

חישוב:

```ts
teachingAmount = round((courseTeachingRate / totalMeetings) * requestedMeetings)
travelAmount = round((courseTravelRate / totalMeetings) * requestedMeetings)
```

אם חסר `totalMeetings` או `courseTeachingRate`, לא מנחשים. הדרישה מסומנת לבדיקה ידנית והסכומים הפנימיים נשמרים כ-0 עד טיפול צוות.

אם חסר `courseTravelRate`, נסיעות פנימיות מחושבות כ-0.

## 14. מגבלות ידועות

- עד שלא ייווצרו השדות החדשים במאנדיי ויוזנו Column IDs, יצירת פריט אמיתי תחזיר configuration error ברור.
- מסלול שיעורים פרטיים עדיין דורש מקור תעריף אמין כדי לחשב סכום פנימי ללא בדיקה ידנית.
- אין DB ואין היסטוריית משתמש מקומית; כל אמת המידה היא Monday.
- אין אימות משתמשים בגרסה הזו.
